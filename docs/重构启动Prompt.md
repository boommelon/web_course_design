## 重构目标

把系统改成真正的“毕业设计管理系统”，不是普通选题/选课系统。核心业务必须围绕：

管理员准备基础数据  
-> 教师出题  
-> 专业负责人审题  
-> 学生第一轮填 1-3 个志愿  
-> 专业负责人确认第一轮最终分配  
-> 未分配学生进入第二轮  
-> 专业负责人确认第二轮最终分配  
-> 仍未分配则强制分配  
-> 学生上传资料  
-> 教师评分评语  
-> 管理员/专业负责人查看结果

## 必须遵守的业务规则

1. 管理员和专业负责人不能混淆。
2. 角色应至少包括 `admin`、`director`、`teacher`、`student`。
3. 管理员只负责基础数据、账号、专业、阶段开关、结果查看导出。
4. 专业负责人负责本专业题目审核、第一轮/第二轮确认、强制分配。
5. 教师负责出题、查看自己指导的学生、资料审核、成绩评语。
6. 学生只能看自己专业的审核通过题目。
7. 学生提交的是志愿，不是最终选中。
8. 每个学生每轮至少 1 个志愿，最多 3 个志愿。
9. 同一学生同一轮不能重复选择同一题目。
10. 一个题目每轮最多被 3 个学生填为志愿，不管是第几志愿。
11. 第一轮结束后，只有未分配学生和未分配题目进入第二轮。
12. 第二轮后仍未匹配，由专业负责人强制分配。
13. 最终必须一人一题、一题一人。
14. 数据库层必须用唯一约束兜底 `final_assignments.student_id` 和 `final_assignments.topic_id`。
15. 题目审核通过后教师不能再修改。
16. 没有最终题目的学生不能上传资料。
17. 成绩可以先做简化版：指导教师给成绩和评语；不要做成“期中/期末/总评”课程成绩模型。

## 数据库连接要求

- 项目数据库访问必须按 JDBC 思路实现，但不要在每个 DAO 方法里重复写 `DriverManager.getConnection(...)`、`Class.forName(...)` 等连接代码。
- 数据库连接、查询、更新、关闭资源等通用逻辑必须集中放在统一工具类中，例如当前项目已有的：
  `src/main/java/util/SQLHelper.java`
- DAO 层应优先调用 `SQLHelper` 的统一方法，例如 `executeQuery`、`executeUpdate`、`queryForList` 等封装方法。
- 如果某个业务需要事务，例如提交三志愿、确认分配、强制分配，可以在 DAO 或 Service 逻辑中只获取一次 `Connection`，然后在同一个事务内完成多条 SQL，最后统一 `commit` / `rollback` / `close`。
- 不要出现每写一个 DAO 方法就单独手写一遍：

```text
Class.forName(...)
DriverManager.getConnection(...)
conn.createStatement(...)
conn.close()
```

- 数据库连接参数、驱动加载、资源关闭必须集中维护，避免散落在各个 DAO 中。
- 重构时如果发现现有 DAO 里大量直接 `SQLHelper.getConnection()`，可以保留事务场景；普通增删改查应尽量改为调用 `SQLHelper` 的统一封装方法。

## 重构优先级

### 第一优先级

- 数据库结构重做或调整
- 新增专业/学院/专业负责人相关数据结构
- 新增 `director` 角色
- 拆分“志愿申请”和“最终分配”
- 实现 `selection_applications`、`selection_choices`、`final_assignments`
- 实现系统阶段控制
- 实现教师出题、专业负责人审题
- 实现学生三志愿选题
- 实现专业负责人第一轮/第二轮确认
- 实现强制分配

### 第二优先级

- 资料上传必须基于 `final_assignments`
- 教师只能查看自己题目下最终分配到的学生
- 教师评分评语
- 学生查看最终题目和成绩
- 管理员/专业负责人查看结果

### 第三优先级

- 公告、统计图、模板下载、AI 助手等非核心功能可以保留，但不要优先做
- 页面美化不是重点，业务正确性优先

## 实现要求

- 尽量沿用当前项目 Servlet/JSP/DAO/Bean 风格，不要随意引入 Spring Boot 或新框架
- 先从 `sql/init.sql`、`src/main/java/util/SQLHelper.java` 和核心 Bean/DAO 开始
- 修改 Controller 时注意权限校验和阶段校验
- JSP 页面只服务核心流程，不要做无关大改
- 不要把最终分配结果继续混在 `topic_selections` 里
- 不要只靠前端限制，核心规则必须后端校验
- 完成后运行可行的编译或检查命令，并说明是否通过
- 如果现有实现和需求冲突，以 `docs/01-实际数据流与业务逻辑需求报告.md` 为准

## 建议的重构顺序

1. 先整理数据库结构和基础实体。
2. 再统一 JDBC 访问方式，收口到 `SQLHelper`。
3. 然后补 `director` 角色与权限控制。
4. 再做题目审核和三志愿选题流程。
5. 再做第二轮、强制分配、资料上传、成绩评定。
6. 最后再处理页面整理和非核心功能。

- 如果发现某个现有表结构或 Controller 和新需求冲突，直接按新需求改，不要为了兼容旧逻辑保留错误流程。
